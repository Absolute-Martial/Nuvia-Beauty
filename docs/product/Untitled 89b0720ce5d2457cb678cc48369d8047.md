# Purpose

This document draws the **MVP Hard Line**. It separates what must be built now from what is deferred, so readers never mistake future vision for an MVP requirement. The Concept Paper, White Paper, Technical Proposal, and implementation plan all defer to it for scope.

<aside>
✅

**MVP success definition:** MVP success is defined by validating customer demand and recommendation quality. Features that do not directly contribute to this validation are considered post-MVP unless explicitly marked otherwise.

</aside>

# 1. Vision

Nuvia Beauty is a consent-driven confidence-shopping system for beauty retail that can grow into a three-sided ecosystem connecting customers, sellers, and manufacturers/brands, and that progressively reduces dependence on third-party analysis APIs through its own custom model. The vision is real and worth designing for — but it is **not** the build plan.

# 2. MVP (build now)

The MVP is a single, provable, demoable loop: **consultation → analysis → structured profile → deterministic recommendations with reasons and warnings → save/reopen**, running end-to-end in demo mode without live credentials.

- Seller-assisted capture / upload with a capture-quality gate.
- One backend-only AI analysis path (Perfect Corp P0) **or** demo-mode fallback.
- Structured, versioned profile snapshots.
- Deterministic, explainable recommendation scoring (reasons + warnings).
- Quota control and demo fallback.
- Basic capture consent only — permission to capture or upload a photo. **Full tiered consent (T0–T4) is post-MVP.**
- Private media via signed URLs; no raw bytes in MySQL; full audit logging.
- Storefront, admin-panel, and vendor-portal frontends over the **single backend API**.

# 3. Post-MVP — Phase 10 Expansion (V2+, after MVP validation)

<aside>
ℹ️

"Phase 10" and "Phase 11" here denote post-MVP **expansion waves** that follow the canonical 0–9 build roadmap. They are not fractional phases and are not part of the MVP sequence.

</aside>

Build only after the MVP validates demand and recommendation quality:

- Personalized shop-branded domains and branded profile reopen (design Phase 7).
- Customer self-scan and deep profile history (design Phase 8).
- Makeup Try-On Studio / VTO (design Phase 9).

# 4. Post-MVP — Phase 11 Expansion (V2+)

- Manufacturer / brand portal (anonymized demand insights, product-fit feedback).
- Consent-governed brand sharing surfaces (T3/T4 activation).
- Full tiered consent model (T0–T4) with revocation semantics and audit trails.
- Multi-provider AI fallback chain in production.

# 5. Future ecosystem (build only if the business proves viable)

- Custom analysis model in production (cold-start → distill → own model).
- Targeted sampling and cross-shop loyalty / continuity.
- Authenticity / anti-counterfeit checks, ingredient-compatibility engine, advanced ranking / vector search, gamification / social.

# 6. Explicit non-goals

- No native mobile app for MVP features.
- No clinical, medical, or diagnostic claims — ever.
- No frontend provider calls; no credentials or storage secrets in the browser.
- No public private-media URLs; no raw image bytes in MySQL.
- No upward sharing of raw images to brands.
- No multi-provider AI, brand portal, or custom model in the MVP.
- No standalone microservices in the MVP (see Architectural Runway).

# 7. Architectural Runway Principle

The architecture is provisioned for the future without building the future today:

- The **Modular Monolith** and database schema are designed to accommodate later features (e.g., a `brand_id` column may exist now; consent tables ship early).
- The **application logic, APIs, and UIs** for post-MVP features are **not** built in the MVP.
- Reserving schema/space for V2+ is allowed; building V2+ behavior is not. This keeps later migrations cheap without polluting the MVP build.
